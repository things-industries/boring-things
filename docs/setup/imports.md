# Import process

One Import processes one Thing. This keeps identity selection, confirmation and retry simple for the MVP, even when several Attachments are submitted. [The roadmap](../requirements/roadmap/MILESTONES.md) covers multi-Thing processing and candidate selection. Fastify owns validation and persistence. Model tasks propose information and include sources when available.

## Entry points

- Uploads start Attachment transcription independently. Plain text is decoded directly. PDFs use local text extraction per page; pages without text are rendered locally and read by Google Vision OCR, as are uploaded images. The `summarize-attachment` AI task receives the resulting text and returns summary, terms, identifier observations, display metadata and language/readability status. Uploaded images with fewer than 500 characters of trimmed OCR text also supply their original image to that same task. Visual observations stay in the summary; transcription keeps only extracted text. Images without text can supply a visual summary for Thing identification and later import stages. Attachment processing commits extracted text before model analysis. Analysis failure leaves the text available with `PARTIAL` status. Invalid metadata properties are omitted independently, and language assessment keeps the extracted text. Missing credentials or OCR errors fail transcription. Sources without recognised text or an understandable visual summary finish as empty. `POST /api/imports` accepts up to ten Attachment IDs and optional Thing context. The Import waits for submitted sources to finish or fail, then uses readable sources.
- Thing context supplies the target for ambiguous scraps. Contradictory identity evidence produces `wrong_thing`. An open Import without an identifiable Thing produces `no_thing_identified`.
- An Import without Thing context selects the strongest candidate and uses semantic matching against the user's existing Things. Identifiers such as model numbers can coincide across manufacturers, and variations in formatting can hide a match. Field-specific normalisation and checks across related identifiers are candidates for improving matching.
- **Find more details** submits an Import with Thing context and no new Attachments. It starts at Research and uses existing linked content during population.
- **Refresh recommendations** calls `POST /api/things/{thingId}:recommend`. It runs the same Recommendation capability that finishes Imports.
- Manual creation saves a Thing directly. Empty Import input without a Thing completes without work.

## Workflow

[ImportWorkflow](../../server/src/application/import/workflow.ts) persists the following stages:

1. **Identify.** Extracted source text is reviewed in bounded summary requests while the complete text is saved separately. Use source summaries, terms, possible printed identifiers and bounded transcription searches. Validate the category, any match to a user's Thing and source citations. Create or match the Thing, add mandatory fieldsets, save identifiers and link relevant sources in one transaction.
2. **Research.** Applicable specialist providers return registry field and fieldset proposals. Each provider's accepted changes and completion checkpoint are saved before public research. Icecat is enabled by `ICECAT_ACCESS_TOKEN`. For appliances and devices, `common.gtin` triggers a GTIN lookup; otherwise `common.manufacturer` plus `appliances.productCode` or `common.model` triggers a brand/product-code lookup. Product code takes precedence over model. Serial numbers and manufacturer alone do not trigger it. Returned GTIN or brand/product-code identity must match before fields are saved.
3. **Find resources.** Reuse shared Attachments with registry-linked class coverage, then search public sources using eligible public fields and category hints. Include the name resolved from submitted sources so model years and generations remain available during resource and recommendation research. Requests without submitted sources use public fields. Resource research uses one model conversation with hosted web search and a `read_resource_page` tool for extracting direct PDF and image links from observed model or support pages. Image-link extraction recognises transformed URLs and responsive image candidates. The conversation allows three hosted web calls and three page reads. Each page read returns up to thirty links within 20,000 characters, with surrounding text shortened as needed. The model returns structured resources and may suggest a display name for the existing Thing. Apply that suggestion to a newly imported Thing unless the user has edited its name; field selection and recommendations use the updated name. Download proposed PDFs and images through the existing protected retrieval helpers, using an application User-Agent for sites that reject requests without one. Save them as shared Attachments, link them to the Thing and Import, and await independent transcription for documents. Product photographs skip transcription and field/recommendation evidence, including photographs saved by earlier imports. Assess document applicability and save group/class identifier coverage for reuse.
4. **Select fieldsets.** Review applicable linked-source summaries and terms. Validate selections against existing category fieldsets and materialise empty field occurrences.
5. **Populate.** Search saved transcriptions for enabled field targets in batches of twenty. Validate field membership and value schemas; omit mismatched quotations and page references. Public resources supply class data. Read the current Thing under a row lock and recheck its population permissions and cited source links before saving each batch.
6. **Additional information.** Fit private uploaded text into initial requests of up to 100,000 characters including instructions and field labels. Keep up to ten significant findings per batch about identifying, operating, maintaining or administering the Thing. Search registry fields before proposing custom fields. Reuse existing occurrences and preserve protected values. Invalid findings are omitted individually; task failures produce retryable warnings while recommendations continue.
7. **Recommend.** One management-task AI task and one purchasable AI task run in parallel. Each receives the relevant suggestions from every saved fieldset and checks any eligibility statements against evidence for the Thing. Each reads applicable linked Attachment passages and saved Thing fields, then uses web search when evidence or purchase links are missing. Recommendations may cite Attachment passages, public sources or both. Purchase URLs must be usable HTTP(S) links. Web tool-call budgets apply across the whole task conversation. Usage snapshots and result commits run in sequence; retry reuses each completed operation. Save suggestions without replacing existing user decisions. Intervals remain descriptive; scheduling belongs to the user.

[AI tasks](../../server/src/providers/ai/tasks/task.ts) share SDK execution for buffered and streamed responses, conversation history, validated structured outputs, typed tools, cancellation and usage reporting. The base class receives execution resources at construction, constructs the SDK client on its first request and wraps the parameterless `runTask()` implementation with a typed, parameterless `run()` method. Every task receives its inputs through its constructor. Tasks register a completion callback with `onTurnCompleted()`; awaited usage persistence stays in the execution context. Each task module defines its task-specific inputs and model outputs beside its prompt, output schema and result conversion. Application modules define domain return types, which tasks import and return. Shared domain types stay in application modules.

Each task owns its model selection. Thing-oriented tasks include the shared Thing definition in their instructions; attachment summaries and delegated public research use their own evidence rules. Both recommendation tasks receive field labels, descriptions and validation schemas alongside values. Each task owns its instructions; shared recommendation instructions stay with that capability. Definitions and evidence rules shared across capabilities are Markdown files in `providers/ai/prompt-content/`, loaded by `providers/ai/prompts.ts` and composed by tasks; import read tools stay in `providers/ai/tools/` and own their execution, call limits and usage recording. Callers pass inputs and an `ImportTaskContext` to task constructors. The context contains authorised source text, category, retrieval records and tool budgets alongside job execution resources. `AiContext` contains the job cancellation signal, an optional `beforeRequest` callback that consumes the shared model-request allowance across tasks and retries, and an awaited `record` callback for usage persistence. Text limits are class settings on `AiTask`, overridable by tasks. The context itself is not included in prompts; source reads return bounded passages. Database and registry resources are bound when the provider is assembled. Task schemas are independent of the HTTP OpenAPI contract. Task outputs and tool arguments use `FromSchema` from `json-schema-to-ts` to infer types from their authored schemas during type checking. The object-schema helper preserves literal types and marks every declared property required. Shared schema fragments use `as const`; model responses and tool arguments still pass through AJV validation at runtime. The application awaits every proposed write. Authenticated revisioned Import and Thing SSE snapshots expose progress without raw source text.

Source-evidence comparisons trim and collapse whitespace on both sides. Extracted text keeps its original formatting. An identifier observation, field proposal, coverage claim, additional finding or source-based suggestion with a mismatched quote or invalid page is skipped individually; other source content continues through the workflow. Extracted identifier labels, values and saved quotes also use trimmed, collapsed whitespace.

## Suggested tasks

Task suggestions prioritise activities specific to the Thing that help maintain it and are easy to forget, such as running a maintenance programme, using pyrolytic cleaning, replacing a consumable or booking a service. They include recurring work and relevant one-off administration. Extremely obvious actions, work likely to happen very frequently during normal use, passive waiting and rare incident recovery are excluded. Common remedies that nearly every user is likely to need, such as resetting a router, can qualify without a recorded fault; descriptions explain when to use them and their consequences. Boring Things handles importing identifiers, policy details and documents.

Supplied age, mileage, condition and service history guide selection of applicable work, such as the documented car service for its age and mileage. Missing facts remain unknown; descriptions give documented conditions without assuming work is due. Prompts ask for evidence recommending the action for the Thing and relevant component when available. Warnings, chemical mentions and identifying labels alone do not justify maintenance tasks.

Titles name the procedure or outcome with a verb and object, such as **Use the pyrolytic cleaning function**. Frequency, conditions, preparation, precautions and completion steps belong in descriptions. Removing coarse dirt belongs in the pyrolytic cleaning description; removing food residues during normal oven use is routine care. Fieldset task candidates can include suggested importance and recurrence. The model checks applicability, uses a documented interval when available, and labels any estimated calendar interval in the description. Suggestions represent each underlying action once. Task recommendations compare supplied existing tasks by meaning, including completed and dismissed tasks. Both recommendation tasks receive linked Attachment summaries, field definitions and values, eligible public research fields and existing suggestions. Their tools may read private evidence and search the public web in the same conversation. Prompts direct web queries to public model, provider and product details. Application checks exclude matching existing titles.

## Validation and omitted results

Imports favour useful information despite incomplete citations. Public recommendation and resource URLs do not need to match search results. Attachment citations must refer to an authorised source; quotations or page references that fail matching are omitted while the proposed information is saved. Recommendations allow empty source lists. A product requires a usable HTTP(S) purchase link; a rejected link omits that product. Downloads continue to enforce address, DNS, content and size restrictions.

Model response arrays are validated one member at a time. Existing registry IDs and category membership govern field selection; prior retrieval through a search tool is optional. Invalid field values, duplicate proposals, unrequested fields and pins are omitted. Public sources supply only `GROUP` and `CLASS` fields. Access checks, user edits, field types and transaction failures continue to govern writes. Applicability assessment errors leave public documents available for subsequent tasks; an explicit inapplicability result excludes them.

Completed imports show that optional work was omitted when a stage has a retryable warning. Skipping an invalid individual proposal completes that batch; a new import can revisit it. Retries resume unfinished operations.

## Fields and user decisions

`bt.thing_fields` stores values, occurrence addresses, provenance and `auto_populate`. Thing metadata retains fieldset selection, pins and user decisions. API responses project field occurrences into fieldsets, standalone fields and custom fields.

Automatic pin suggestions prioritise identifying details and fields the user is likely to consult frequently. The population task considers existing and newly found values, giving generic descriptions that repeat the Thing's name or category lower priority. Each batch can suggest up to three populated requested fields; the workflow adds pins until three are saved and keeps user-edited pins.

Field definitions classify attributes by `scope`: `GROUP` for manufacturer/provider attributes, `CLASS` for model/plan attributes, and `INSTANCE` for the specific item, account or agreement. `isIdentifier` marks fields that contribute to Thing identification. Public research uses populated `GROUP` and `CLASS` fields independently of sensitivity. Purchase date, price paid and order reference are `INSTANCE` attributes without an identity role. Custom fields use the same scopes and default to `INSTANCE`; they do not participate in identity matching.

Mandatory fieldsets have null eligibility. Each category has a mandatory set, and each category identifier has a designated mandatory occurrence so specialist lookups can run before optional fieldset selection. Empty registry fields added manually remain eligible for population. Imported fields are eligible. Manual values and custom fields disable automatic population. Manually clearing a registry value keeps an empty disabled occurrence. A `ValuePatch` can change `autoPopulate` alone while keeping the value and provenance. Every automatic writer uses the same permission check.

Category changes add the new required fieldsets and move fields with one occurrence in both layouts, including their provenance, pins and automatic-population permissions. Other populated values become custom fields for review and are excluded from public research. Removing a populated fieldset also keeps its values as custom fields. User-removed fieldsets, custom fields and Attachment links are recorded so automatic work cannot restore them.

A Thing's category can change once its current request finishes. Earlier requests remain in import history and cannot be retried for the new classification. **Change category and find details** queues a fresh Import in the same transaction as the category change. The Import uses linked transcriptions and reassesses public documents before using them as evidence. The category change clears an automatically chosen public image and removes generated purchasables and unedited Task suggestions. The Attachment links, user-selected image and accepted Tasks stay with the Thing.

## Shared resources and access

User uploads remain private. Discovered public resources are saved once with shared content, transcription, public metadata and identifier coverage. Each user sees only their own Thing links. Import and citation references also retain access to public evidence after unlinking.

Users may unlink shared resources. Shared metadata and content are system-managed, and user-specific choices belong to the Thing link. Private Attachment deletion is rejected while a Thing, Import or citation still references it. Deleting a Thing removes its job and links while keeping shared files. Any future shared-resource cleanup must account for links, Imports, citations and image selections before deleting the file.

## Execution and recovery

[JobRunner](../../server/src/application/jobs/runner.ts) runs Import/Recommendation, transcription and chat processors concurrently. Each processor handles one job at a time. The dedicated PostgreSQL session lock lets overlapping deployments use the same database without two runners claiming work. Recovery runs after acquiring the lock, and shutdown awaits all processors before releasing it.

Identity, specialist results, resources, field batches and recommendations have saved checkpoints. Application changes and completion records share a transaction. Retry reuses completed work, requeues failed source transcription and resumes unfinished stages. Source fingerprints make changed transcription or links eligible for renewed field work, and commit-time checks skip proposals citing changed or removed sources. Unrelated proposals continue. A fresh Import or Recommendation starts new work for the existing Thing.

After a restart, recovery requeues Imports and transcriptions still marked as in progress. An Import that saved an interruption during shutdown is available for user retry. An interrupted assistant response becomes a retryable failure.

Identity failures become explained errors. Failed Imports save the stage and a bounded failure reason in the internal workflow checkpoint; retry removes that failure record. Optional research and recommendation failures retain retryable warnings and saved results. Invalid individual proposals, field IDs and pins are omitted while valid peers continue. Optional fieldset-selection and population failures create retryable warnings and allow subsequent stages to run. Persistence failure prevents a completion checkpoint. Completion and errors release processing restrictions. The frontend shows unfinished work and offers retry, including completed jobs with warnings.

## AI task configuration

Provider log task names follow task filenames using underscores. `find-resources.ts` logs its requests as `find_resources`; `assistant-research.ts` logs delegated chat research as `assistant_research`.

Each task declares its model and reasoning effort in `server/src/providers/ai/tasks/`. The base task sets standard reasoning mode for every request. The base task reads `OPENAI_API_KEY` through `getEnv` on its first request and sets limits. Task classes override shared limits where needed; each research task sets its web search limit to three calls. Application configuration controls workflow budgets and deadlines. Provider assembly rejects missing credentials at startup. Task properties own model, reasoning and request settings. The base task computes hosted-search allowances and tool finalisation for each turn; text limits include task instructions. Buffered and streamed refusals report `ai_refused` after recording usage. Task model choices apply to imports, recommendations and chat.

## Limits and configuration

Set `GOOGLE_VISION_API_KEY` for images and PDF pages requiring OCR, enable Cloud Vision API and billing in its Google Cloud project, and restrict the key to that API. Restart the API after changing environment variables. The `providers/google-vision` module calls `DOCUMENT_TEXT_DETECTION` through REST with the credential in a request header. Original files stay in attachment storage. PDF parsing and rendering run in a worker with a 256 MB heap limit. Pages without embedded text are rendered at up to twice their PDF dimensions, capped at four million pixels, and sent through the image OCR endpoint one page at a time. Combined text keeps original `[PDF page N]` labels and is bounded to 1,000,000 characters. Request copies above 7 MB are encoded as JPEG at the original dimensions first, then resized once if needed to fit Google's 10 MB JSON request limit; copies still above the limit fail. Each OCR request has a 30-second deadline within the attachment's existing deadline. The 15-second parsing deadline pauses during OCR and restarts when parsing resumes. No SDK or additional storage service is required.

Google Vision completion logs contain elapsed time and image count under `metrics`. Attachment usage records the OCR operation as `google_vision_ocr` without treating it as model token usage. Automated fixture tests substitute OCR text and never call Google.

| --------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Submitted Attachments       | Ten per Import                                                                                                        |
| Linked-source review        | Twenty per run; additional sources produce a warning                                                                  |
| Resource discovery          | `IMPORT_MAX_RESOURCES`, default three                                                                                 |

Upload size, PDF parsing and image decoding also use the limits in the retrieval helpers. Request entries record model, token usage and latency; Import usage includes source transcription usage and records tool calls and elapsed time. Recommendation and additional-information tasks can request independent local reads together within each lookup round. The server caps the calls and combined evidence returned per round. When local lookup rounds run out, the model can use its remaining web searches before answering from the gathered evidence. Request, text and timeout limits still apply. Other limit failures keep committed work for review or retry with revised configuration.

Icecat uses the [Product JSON API](https://iceclog.com/manual-for-icecat-json-product-requests/) with the token in the `api-token` header. Free Open Icecat access covers participating brands such as Philips; absent, restricted and unreleased products return no proposals. Authentication, transport and malformed-response failures create retryable warnings. No brand list is hard-coded. Mapped fields include manufacturer, model, GTIN, unqualified overall dimensions, appliance finish and electrical supply, and device weight, screen diagonal and display resolution when supplied. Feature IDs select meanings and display values keep units; package and stand-specific dimensions are omitted. The shared writer applies automatic-population permissions. Run `pnpm db:seed` and restart the API after updating the registry. No provider credentials reach the browser.

Specialist integrations extend the `SpecialistProvider` base class in `server/src/providers/specialist-data.ts`. The base class holds the request function and defines applicability and lookup methods. The Import workflow saves results through the field writer and manages completion checkpoints and optional warnings.

### Vehicle lookup

[Zyfy](https://zyfy.uk/docs/vehicle) runs before public resource research when `ZYFY_API_KEY` is configured and the saved Thing has a registration matching a UK plate pattern. The check accepts current, prefix, suffix and dateless shapes, including personalised plates, without checking issuance rules. An unset registration country allows lookup; a recorded country must be UK, GB, GBR, United Kingdom, Great Britain or one of the constituent countries. The provider checks that the returned registration matches the normalised lookup input.

Vehicle fields include manufacturer, model, body type, colour and year of manufacture. Manufacture year is separate from model year. `vehicles.firstRegistered` stores the first-registration month as `YYYY-MM`; a migration converts existing full-date values and keeps provenance and automatic-population permissions. The field uses a text editor with month validation.

Road vehicle specifications include fuel type, CO2 emissions and London ULEZ compliance. Combustion engine specifications include engine capacity and emission standard. Roadworthiness stores the MOT scheme, status, expiry, first test due date and last recorded test date/result. Road tax stores status, due date and annual cost using GBP minor units. Maintenance includes an outstanding safety recall flag. Unknown values remain unset; false and zero remain values. The shared writer respects user edits and disabled population.

Pending enrichment follows `Retry-After`, with at most three requests and a thirty-second overall timeout. HTTP 404 returns no proposals. Other HTTP, identity, transport and pending-timeout failures create optional lookup warnings; retry resumes that provider. Completed lookups are reused when another stage is retried. Each HTTP request records provider telemetry without registration or response content. Every request can consume provider quota, including pending and not-found responses.

Field source references record Zyfy, the lookup URL, retrieval time and source `dataAsOf` when supplied. Another explicit Import can refresh fields that allow automatic population. Refresh scheduling is not automatic. Source and derived date values can become stale between lookups; days remaining are calculated from dates when needed. Zyfy provides MOT summaries rather than individual test records or defect descriptions. [Coverage](https://zyfy.uk/docs/coverage) and [signals](https://zyfy.uk/docs/vehicle/signals) describe the source data.

Run `pnpm db:migrate`, `pnpm db:seed` and restart the API after updating. The key stays on the server. Provider tests use synthetic responses and make no Zyfy requests.

### Household EPC lookup

Set `EPC_GOVUK_API_KEY` to a bearer token from the [GOV.UK energy certificate data service](https://get-energy-performance-data.communities.gov.uk/guidance/energy-certificate-data-apis) and restart the API. The service is free and covers domestic EPCs in England and Wales.

For a Household import or refresh, the provider uses a user-entered EPC reference or searches the postcode from the saved address. It matches the whole premise, including any flat number, before selecting the most recently registered certificate. If matches conflict, the user can enter the reference in the Energy performance fieldset. When both the full address and the reference are present, they must identify the same dwelling.

The provider proposes the EPC scheme, rating, inspection date, validity end date and reference. It also proposes the UPRN, country, dwelling type, house form for houses, floor area, wall description and the main building's construction period when available. The UPRN is saved as text in Household basics. The provider calculates the last valid day from the registration date and decodes construction age using the certificate's schema version. The saved address comes from the user or import. The lookup sends the postcode or reference directly to GOV.UK, and source links on unmasked fields point to the register without including the certificate reference.

A missing or ambiguous result allows research to continue. Request failures create retryable warnings. Values use the same automatic population permissions and checkpoints as the other specialist providers.

## Validation

`server/test/import/`, `server/test/fields/` and `server/test/jobs/` cover the workflow, automatic-population permissions, shared-resource lifecycle, specialist mapping and concurrent execution. Integration and browser tests use fixture providers and isolated databases. `pnpm check` checks authored and generated contracts, types, lint, unit tests and builds. `pnpm test:integration` requires local PostgreSQL and a built frontend.

The paid smoke script traces the current workflow. Each invocation requires explicit approval under [metered AI validation](../agents/agent-behaviour.md#metered-ai-validation).
